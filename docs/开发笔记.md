## 跨端互通（结论 + 判据，别再重新调查一遍）
- **手机和电脑本来就能一起玩**：`server.js` 与 `index.html` 里**没有任何 UA / 平台 /
  设备分支**，服务端只按房间码找座。手机端只是同一文件上多挂了两段 media query。
- `tools/probe-crossplay.js` 是这条结论的**证据**（不是推理）：它先断言两端形态确实不同
  （电脑端 `.meters` 可见 / 手机端不可见、只有手机端有 `#pingPill`），再让两端互相同房、
  互相看见、各用自己的输入方式驱动对端。**"两端形态相同却报互通成功"是空证据**，
  所以那段形态断言是该探针的核心，不许删。
- ★ **`navigator.maxTouchPoints` 在无头 Edge 上默认就是 10**，拿它判"是不是触摸设备"**恒为真**。
  只有 `'ontouchstart' in window` 与 `(pointer: coarse)` 与
  `Emulation.setTouchEmulationEnabled` 同步（不开模拟时 false）。
  且 `setDeviceMetricsOverride {mobile:true}` **本身不开触摸**，要另调
  `setTouchEmulationEnabled`。
- ★ **`Input.dispatchTouchEvent` 不依赖触摸模拟**：不开模拟也能把触摸事件送进页面。
  所以"手指拖动拍子"证明的是**客户端对触摸有响应**，**不能**用来证明"这端是触摸设备"。
  两个命题分开举证。

## 手机端布局的两条断点（改动前先读这段）
- **窄屏/竖屏**：`@media (max-width: 760px)` → 藏 `.meters`、藏操作说明、
  `.stage { --reserve: 118px }`、`#pingPill` 显示、菜单改 `position:fixed` 整屏抽屉。
- **横屏铺满**：`@media (orientation: landscape) and (max-height: 560px) and (max-width: 1100px)`
  → 页眉 `position:absolute` 不占纵向高度、球场吃满视口高、底色换成球场色。
- **刻意不用 `pointer: coarse`**：视口尺寸是探针能精确控制的量，pointer 媒体特性在
  仿真环境里不可靠 —— 一条没法在测试里复现的断点等于没测过。
- 竖屏提示条 `.rotatetip`（"把手机横过来玩"）必须 `position: fixed`：
  留文档流里会被整屏抽屉盖住。

## 硬约定（踩过坑，别改回去）
- `anyAlive(room)` 只看真人连接：bot 算 alive 会让房间永不回收。
- `findSeat` 必须跳过 bot 座位：否则真人会顶替 AI，人机局变成空转。
- AI = `botPerceive`（限频决定瞄准）+ `botSteer`（每 tick 决定方向），**不可合并**。
- 计分只能走 `afterGoal`（双倍得分要影响胜负判定，不能在 `stepBall` 里直接 +1）。
- `trackMods` 必须复位 `freezeUntil` / `doubleUntil`。
- 一切"拍子半长"的判定都走 `paddleHalf()`（长/短道具会改它）。
- 客户端 `send()` 对 `create`/`join` 做断线排队；`input`/`ping` 不排队。
- 隐形球（道具 8）按**队**生效：`room.invisUntil[team]`，透明度由服务端算好下发（`ia`）。
  渐变方向：`elapsed < FADE` 用 `1 - elapsed/FADE`，`remain < FADE` 用 `remain/FADE`。
- 横屏块里**不要去掉 `.stage` 的 border**：画布只画上下墙（`fillRect(0,0,W,3)`），
  左右两条出界线是靠这个 border 划出来的，去掉之后"球在哪出界"就没有视觉依据。
- 横屏块里 `header` 的 `pointer-events` 是 `header / .hright = none`、**只有 `.soundbtn` = auto**。
  透明的横带不能吃掉球场右上角的触摸拖动。★ **只读的徽章 / 延迟胶囊 `#pingPill` 故意保持
  穿透（pe:none）—— 但它们是照常绘制的**。所以"胶囊到底看不看得见"**不能直接问
  `elementFromPoint`**：它会跳过 pe:none 的元素，返回的是下面那一层（实测拿到 `.overlay`），
  看着像"被盖住了"，实际是一条**恒假的假红**。要先把该元素 `style.pointerEvents='auto'`、
  问完立刻还原（`probe-mobile` 的 `vis()` / `probe-crossplay` 的 `SHAPE` 都这么做）。
  另外竖屏**菜单态**下胶囊被整屏菜单抽屉盖住是**设计如此**（抽屉就是主界面），
  它的可见性判据在"竖屏对局中"那一节，别放回菜单那一节。
- ★ **球必须有横向速度，否则整局死锁**。球只在上下墙之间竖弹时 x 不变 ⇒ 永远碰不到拍子
  ⇒ 这一回合永远结束不了。来路两条：①等质量弹性碰撞的 `approach*dx` 项能把 vx 抹成 0，
  且**一旦变纯竖直就自锁**（两个竖直球正碰只交换 vy，vx 仍是 0）；②分裂球对竖直源球
  走镜像分支，新球横向占比与源球一样。修法见 `unstickBall`：`resolveBallCollisions`
  **之后**调 `unstickBalls(room)`，只**旋转**方向（不改速率，速率是反隧穿论证的前提），
  重瞄到与水平成 30°~60°、左右随机、上下倾向沿用。判据是**占速率的比例**（`MIN_VX_RATIO`），
  不能写绝对阈值 —— 速率会涨到 900，绝对值到后面形同虚设。
- `SPEEDUP_PER_HIT` 现为 **1.075**（原 1.055），出速爬到封顶由 ~14 拍降到 ~11 拍。
  —— 它是**逐次相乘**，别改成"每次加常量"。
- 手机端横屏里 `.solobar`（人机/合作模式的常驻信息条）在**右侧两排**，不能在左下：
  用户实测它压在自己拍子的活动带上（旧位置 x=12、宽 164 → 覆盖 12~176，而左拍列是
  [130,141]）。同理触摸拖动**不能只绑 canvas**：canvas 外的留白也要能拖（`touchHitsUI`
  只放行真正的 UI 控件），否则手指在拍子位置会挡住视线。
- ★ **常驻栏在窄横屏（667×375，iPhone SE/8 那种）必然会压住球场右缘，这是几何决定的**：
  球场 `min(100vw, 100dvh*1.6)` = 600，两侧各只剩 **33px** 留白，而这一栏有 **88px** 宽
  —— 任何点得到的控件都放不进 33px。实测：栏 `[571,310,88,58]` vs 球场右缘 634
  ⇒ 压住球场 **63px**，且压到 AI 拍子列（`[760,774]/800` → 屏幕 `[603,614]`）= true。
  所以 `probe-mobile` 在这一档**只断言"不压自己的拍子活动带"**（可保证），
  压住多少球场只**报数不判**（判了就是一条注定红的假要求）。844×390 那种宽横屏
  留白有 122px，栏整个落在留白里，零重叠。

## 暂停 / 继续（第 9 轮，双人**双方都能按**、按一下算一下）
- ★ `userPaused`（玩家按的）/ `pausedBy` / `frozenAt` 与既有的 `paused`（缺人自动冻结）
  **必须是不同字段**：合成一个会让 `ph` 变 `waiting`，而客户端 `waiting` 分支**不画球**
  ⇒ 一按暂停球就从画面消失；且两种情形的提示语不同。
- 快照 `up`(0/1) 与 `pb`(槽位号，-1=无) **单独下发，绝不并进 `ph`**；客户端**绝不许从 `ph` 反推**
  （反证 F7：改成 `m.ph === 'paused'` 后整条状态链断、7 条红）。
- ★ 冻结期间**逐 tick 增量后移挂钟**（`now - room.frozenAt`），不能"解冻时补一次" ——
  服务端每个快照都用 `nextPowerupAt` / `*Until[]` / `powerups[].bornAt` **算** `fz`/`ia`/`db`，
  只补一次会让这些字段在暂停期间走到"已过期"（玩家看到"暂停中对手忽然又能看见球了"）。
  `bump = (t) => (t > 0 ? t + ms : 0)`（**0 保持 0**）；`phaseEndsAt` 只有 `over` 归它管。
- ★ `room.started &&` 前提不能省：先建房的人闲按一下，第二个人进来就永远卡在"已暂停"。
- `handlePause` 校验 `p.token === ws.player.token`（防掉线顶替后旧连接操作新房）；
  **刻意不做"两边必须同意"**。
- 按钮复用 `.soundbtn`（继承手机 36×36 触控尺寸）+ `style="display:none"`（**不参与布局**，
  桌面菜单态几何基线逐像素不变）。`loop()` 里 `var frozen = !!view.userPaused;`
  要**同时冻结本地预测与触摸跟随**。按钮文字**零乐观更新**，一律以快照为准。
  ★ 诚实记录：零乐观更新的收益窗口只有 ~33ms，**无法确定性证伪**故不写测试；只保护**结果**
  （"两人同时各点一下 = 切两次 = 回到未暂停，且文字跟着服务端走"）。

## 第 10 轮：拍子皮肤 = 技能（青风 / 黄幻影 / 红超高速）
菜单里每局自选皮肤，**颜色就是技能**：灰=没有技能、青=风、黄=幻影、红=超高速。AI 不能选。
释放：手机点球场边上的圆钮、电脑鼠标点、电脑 **Q** 键。技能按**槽位**存
（`skins[slot]` / `skillReadyAt[slot]` / `boostArmed[slot]`），coop 里左边两个槽位同属 0 队
但各人有各人的技能与冷却。冷却：风 10s、幻影 15s、超高速 10s。
- **风**：方向 = 自己拍子中心 → 球场中心（**拍子的实时位置**，不是槽位中点），
  持续 1s；效果是给球加 `dx*WIND_ACC*dt` 的加速度（一个式子覆盖加速/减速/推偏/吹变向）。
- **幻影**：真球与幻影球**等速**对称偏开 `PHANTOM_ANGLE`（0.30 rad），持续 5s。
  释放方**看不到**它、不为它计分、它**不与任何球碰撞**（唯一破绽：对手可能看到两个球
  互相穿过去 —— 已如实写进交付说明）。幻影球出界**不触发** `afterGoal`。
- **超高速**：下一次**自己**击球 `BOOST_SPEED=1400`（刻意高于 `BALL_SPEED_MAX=900`，
  反隧穿靠半空间判定 + 30px 护栏）。

### 这一块的硬约定（每条都踩过）
- ★ `isPhantom(b)` 必须 `typeof b.phantom === 'number'`：`phantom` 存的是**队号**，`0` 合法。
  写成真假判断 ⇒ 0 队的幻影球被当真球（参与碰撞、出界还送分）。反证：改坏后 8 条红。
- ★ **幻影按队过滤只能在服务端做**，`broadcastState` 里**按队分别 stringify**（带缓存）：
  `bs` 过滤掉"属于该队"的幻影球；**`px`（还剩几秒）也必须一起过滤** ——
  只过滤 `bs` 的话，对手看到"自己那格 0、另一格非 0"就确知有幻影。
  对照：蓄力光圈 `bo` 是**故意公开**的（那是"下一板要超高速"的预告），两者不是一回事。
- ★ `removeBall`（幻影出界/到寿）里 `if (room.balls.some((q) => !isPhantom(q))) return;`
  **不能删**：真球出界会走 `afterGoal`，幻影出界不走 —— 少了这句护栏，幻影一出界就把
  正在飞的真球一起换掉（球凭空回中场）。**这条护栏原本没有任何断言保护**，2026-10-10
  做反证时发现并补了断言（test-rules 19.4 末尾）。
- ★ `afterGoal` 的"还有球在飞吗"判据要用**真球**：`!room.balls.some((b) => !isPhantom(b))`。
- ★ `trackMods` 必须清过期的风：`stepBalls` 只 push 不删 ⇒ 每放一次永久多一股合力。
- ★ 风是**唯一**能把球推过 `BALL_SPEED_MAX` 的路径 ⟹ 施力之后必须夹**速率**（不是分量）。
- ★ `shiftDeadlines` 要把技能计时器一起后移：`skillReadyAt[]` / `winds[].until` / `balls[].phantomUntil`。
- ★ `clearSkills` **刻意不动 `room.skins`**：皮肤属于"这一场"，第二局不用重选。
- ★ 邀请链接改成**只预填房间码**、不自动入房：自动进去的人没机会选皮肤 = 用不了技能。
- 技能按钮 `position: fixed`（`.stage` 有 `overflow:hidden`），用 `<button>`
  （`touchHitsUI()` 靠 `closest('button')`）；`syncSkillBtns()` 末尾要立刻调
  `layoutSkillBtns()`（后台标签页 rAF 会停）。皮肤上色 = 填皮肤色 + 描身份色（两条都要）。
- ★★ **幻影球唯一的破绽**：两个球会互相穿过去。这是需求原话（"撞在一起穿过去"），
  不是 bug；交付说明里如实写了。

## 与"测试骗人"有关的两条新教训（2026-10-10）
- ★ **`probe-coop.js` 的"平行竖线"扫描有两个坑**，改之前先读：
  ① 挖球必须用 `ballDisps`（**画出来的**位置）而不是 `balls`（服务端真值）——
  客户端对球做指数平滑，真值最多领先画面 59px；球从左边飞出去的那几帧，真值已在 x<0
  而屏幕上的球还在缝里，拿真值当遮罩会漏掉它，18px 的球体在缝里正好是个 >4 的"竖条"。
  这就是该断言**偶发报红**的原因（本地十几次偶发一次、线上对照全绿）。且分裂球之后
  最多 3 个球，也不能只挖 `balls[0]`（旧实现就是这样）。
  ② 单帧采样会**读到旧画面**（画布只在下一次 `draw()` 才更新）——这条断言是"没有杂线"，
  读到旧画面属于**漏报方向**，比误报更危险。所以改成"两帧、同 x、都 > 4"才算有线，
  且取第一帧前先等 250ms。falsification：往渲染里注入一条 73px 的线
  （patch `CanvasRenderingContext2D.prototype.fillRect`）→ 立刻采样只读到 2px，
  等一帧后读到 73px@x=21，两条断言按预期变红。
- **`C.evalx` 里画 canvas 要用"场地坐标"**：客户端 `draw()` 每帧先
  `ctx.setTransform(dpr,0,0,dpr,0,0)`，所以注入的绘制**不能再乘 dpr**（乘了就画到范围外）。

## 六条通用技巧（本项目验证出来的，别的项目也能用）
1. **canvas 渲染可断言**：`Page.addScriptToEvaluateOnNewDocument` 注入
   `fillText`/`strokeText` 记录补丁，抓真正绘制的字符串 ⇒ 不需给页面加测试钩子。
2. **竞态要确定性复现**：在同一 tick 里 `dispatchEvent(new MouseEvent('click'))` 连点，
   比靠 CDP 往返"碰巧"落进窗口可靠得多；并且写完后**先把代码改回旧行为跑一遍**，
   确认断言真的会红。
3. **先确认"被测变量"在选定的量具尺寸下真的有效**。基线只测 1280×820 时，
   把 `.stage` 的 `--reserve` 从 210px 改成 200px **居然全绿** —— 那个尺寸下球场宽度被
   `max-width:940px` 卡住了，reserve 根本没参与计算，等于选了一个让被测变量失效的视口。
   现在基线采三档，其中 1280×700 / 1024×640 是**高度受限**的，reserve 才起作用；
   并额外有一条元检查断言"1280×700 下球场宽度 < 940"来证明这不是空断言。
4. **"量到了" ≠ "看得见"**：`getBoundingClientRect()` 有面积只证明它在布局里，
   不证明它在最上层 —— 竖屏提示条被整屏抽屉盖住时矩形照样有面积、断言照样通过。
   可见性要用 `document.elementFromPoint(中心点)`，必须返回它自己（或其后代）才算数。
   ★ **但这个量具本身有一个坑**：`elementFromPoint` **会跳过 `pointer-events:none`
   的元素**。目标元素一旦是 pe:none（本项目里的只读徽章 / 延迟胶囊就是），它会永远返回
   下面那一层 ⇒ **恒假的假红**。所以要先临时 `el.style.pointerEvents='auto'` 再问，
   问完立刻还原（页面的持久状态一点不动）。
   ★★ **但"临时放行"只回答另一个问题，不能代替原问题（2026-10-10 修正前面的说法）**：
   它回答的是"**如果**它能被点，这点上最上面的是不是它"，对"它到底能不能被点"**毫无信息量**。
   反证 F8 实测：把横屏块里的 `header .soundbtn { pointer-events: auto; }` 删掉，
   临时放行那条**照样全绿**（`hitSelf:true`），而真手指点下去完全没反应。
   ⇒ **两条都得留**：`hitRaw`（不动手脚 += 返回的就是它自己）与 `hitSelf`（临时放行）。
5. ★ **"量具检查"本身会把被测变量推进饱和区，于是把断言变成恒真**。F6 实测：
   我为了证明"本地预测也冻结"写了 `selfP0 === selfP1`，前面又加了"未暂停时按方向键拍子会动"
   的量具检查（400ms ArrowUp）—— 那把拍子从 250 推到 34、**被 `Math.max(lo, …)` 夹在上界 40 上**，
   于是之后"暂停中按 ArrowUp 不动"在**本地预测根本没冻结**的坏实现下**照样全绿**。
   ⇒ 凡是被 `clamp`/夹取/取整/阈值门限过的量，"没变"都必须在**远离边界处**才有意义。
   修法：**两个方向都测**（上 700ms + 下 1400ms，两段都不许动），改完 F6 立刻红
   （`起始48 →按上48 →按下95.4`）。
6. ★ **`--headless=new` 下后台标签的 `visibilityState` 是 hidden，`rAF` 被节流** ⇒
   "画布上画了没画"这类断言会在**同一份代码**上时而绿时而红（实测：同一实现连跑，
   第二次报 `700ms 内画了 0 次文字`，连带 7 条红）。且 `Page.bringToFront` **有时来不及**。
   根治：起浏览器时加 `--disable-background-timer-throttling
   --disable-backgrounding-occluded-windows --disable-renderer-backgrounding`。
   ★ 它**解决不了** `Input.dispatchTouchEvent` —— 触摸仍只能送到前台标签页（后台标签 CDP 超时）。
   6b. **"球在动"这类断言不能只比两个采样点**：刚进球时球会被重置到球场正中（`400,250`）
   并停在整个倒计时里（实测撞到 `400,250 -> 400,250` 的假红）。改成**有界重试**
   （4 秒内出现过位移即算过）。

## 别的坑（也通用）
- **"没收到"和"没推进"必须能分开**：`test-protocol.js` 第 5 节曾偶发报
  "只见过 countdown / 球没动"，看着像服务端卡在倒计时，实际是那个 22s 观测窗口里
  A 一帧都没收到。已加前置断言"窗口内确实收到 ≥5 帧新快照"。
- ★★ **"两块拍子都不动"的房间里，发球有 74% 直接得分**（算过一次：发球角是 ±0.54 rad
  的随机值，飞到对面纵向偏移最多 240px，而拍子只覆盖 ±57px；只有 |角度| ≤ 0.14 的那 26%
  会被挡回去）。所以一切"等一个不会进球的窗口"的探针都是在**抽奖**，
  红出来的样子和"功能坏了"一模一样。**修法是给探针加陪练**（见下一条）。
- ★★ **陪练（`waitBallFresh(sess, ms, guards)`，`tools/probe-skills.js`）**：
  用**键盘事件**（`window.dispatchEvent(new KeyboardEvent('keydown', {key:'ArrowUp'}))`）
  把某一侧的拍子对准"球到达时的那一行"（要算上下墙反射），球就会被一定接回去。
  三条实测结论：
  ① `onKey → setDir()` 是**同步**的 ⇒ 派发的事件在**后台标签页也生效**；
  ② 触摸那条路走 `touchTargetY`，它在 **rAF 里**被消费 ⇒ 后台标签页推了等于没推
     （这是"客户端对触摸有响应"之外，又一组必须分开举证的事）；
  ③ 拍子位置要读 `paddle`（服务端真值），**不能读 `paddleDisp`** —— 后者每帧在 rAF 里
     更新，后台标签页里是**冻住的**，拿它当反馈会一直跑偏。
  ④ 陪练**只能由那一页自己发键盘**（服务端按 socket 认人）：两端都安排上，比分就永不涨、
  窗口一个接一个。加了之后 `probe-skills` 从 49s/易红 变成 20s/连跑三次 79 全绿。
  ⑤ 有一个例外：**超高速那段只陪练红方**，两条都陪练的话球一定被打回来，
  蓄力会在断言读它之前就被正当消耗掉。
- ★ **菜单里第一个 `<button>` 已经不是「建房」了**：加了皮肤行之后排在最前面的是 4 个
  `.swatch` 色块。`querySelector('#overlayBody button')` 只会"选个皮肤"，房间压根没建起来
  —— `probe-bgm` 就因此红了 3 条（没进房间 / tickRate=0 / snaps=0），
  看起来像音频把主线程搞死了。**探针点菜单按钮一律点名**（`.primary` / 按文字找）。
- ★ **触摸事件会被"覆盖层还在"静默吃掉**：`touchHitsUI()` 把落在
  `.overlay/.panelbox/.solobar/.rotatitip/button` 上的触摸**有意排除**（免得点按钮被抢成拖动）。
  所以进对局之后必须**等 `__probe().overlayHidden === true`** 再拖拍子 ——
  `probe-mobile` 4a 那条"手指下滑拍子跟着走"就红在这儿（调试副本量出的铁证：
  那一刻 `elementFromPoint` 命中的是 `.overlay`，`pointer-events:auto`）。
  症状"拍子没反应"与"触摸坏了"完全同形。**不是产品回归，是探针少了前置条件。**
- ★ **本机 `spawn(node)` 一律 EBUSY**（沙箱的进程垫片挡的，`process.execPath` 也挡）。
  所以"自己起子进程跑测试"的脚本在本机会**静默什么都不做**。
  反证/批处理要由 **bash 驱动循环**，node 只负责文本改写（`apply` / `restore`）。
- ★ **反证要写清"预期哪一条断言变红"**，并且允许"红在隔壁那条"：
  "蓄力对所有拍子生效"改坏后，红的是更直接的那条
  `而且那一板也没有变成超高速 -> 1400`，而"没吃掉我的蓄力"那条仍然成立
  （因为我的改法只动了判据、没动清蓄力那句）。**这不等于护栏缺失**，报告里要如实写清楚。
- `grep -c` 无匹配时退出码是 1，放在 `&&` 链中间会**静默截断**后续所有校验命令。
- 本地服务器必须用 `run_in_background` 起；`cmd &` 会在工具调用结束时被杀掉，
  并且留下一个 `EADDRINUSE` 的假象。
- ★ **服务端反证必须重启进程**：改磁盘上的 `server.js` 不会影响已加载的模块（客户端不用，
  静态文件每次导航都重读）。改完 `server.js` 记得 `taskkill` 掉 3100 上的进程再重启，
  否则你会对着旧实现跑测试。**kill 掉进程会连带结束那个后台任务**，属正常。
- 起无头 Edge 的地方一共**四处**：`tools/cdp.js`（`probe-mobile` 等复用）、
  `tools/probe.js`、`tools/probe-crossplay.js`、`tools/probe-bgm.js`。
  改启动参数（如上面那三个防节流开关）四处都要改。`probe-powerup-fx.js` 只 spawn **server**。
- ★★ **探针里绝不要写 `if (拿到东西) { 一堆 check }`** —— 条件式断言会**藏故障**。
  实测：7 条依赖断言包在 `if (wind) {}` 里，被破坏时报告是"38 通过 / 1 失败"，总条数从 46
  **掉到 39** —— 7 条断言凭空消失。**"消失的断言"和"通过的断言"在报告里长得一模一样**，
  于是"整条链路断了"被读成"轻微故障"。修法：无条件执行，拿可能为 `null` 的值去判，
  没拿到时这些断言一起红、理由栏写"无风可判（上游那条已经红了）"。**条数必须恒定。**
- ★★ **"先等窗口、再做耗时动作"是必错的写法**。第 12 节第一版：等 `playing` → 顶拍子 1.4s
  → 再按技能，线上跑出 **"按了 0 次"**（看着像产品坏了）。根因是这一局的真实时间结构：
  `COUNTDOWN_MS = 1800`，而且**每次进球 `resetBall` 都会 `phase='countdown'`** ——
  两端都不陪练时一回合 = 倒计时 1.8s + 球飞过去一两秒 ⇒ **`playing` 窗口只有一两秒**，
  等拍子顶到位时早回到 countdown 了。
  **修法：** ① 用"**持续按住**"代替"顶到位就松手"（顶到夹取边界后再按也不动 ⇒
  "那一刻拍子在哪"变成常量，不依赖时序）；② 等到窗口后**立刻**动作，中间不插任何耗时步骤，
  失败靠重试兜底（**被拒的技能不扣冷却 ⇒ 重试安全**）。
- ★ **`startMatch` 会把两块拍子复位到正中央**（`paddles = slots.map(s => (s.span[0]+s.span[1])/2)`）。
  所以"先把东西摆到位、再慢慢等窗口"可能等到的是**下一局** —— 摆放全被冲掉。
  `resetBall` 则把 `phase` 打回 `countdown`（每个球都这样）。这两条合起来决定了
  "拍子位置"必须靠**持续按住**来维持，而不能靠一次性摆位。
- ★ **产品已经上线后，反证要反过来做**：改**本地** `server.js`、用一个**临时端口**起个服务，
  把**同一个探针脚本**指过去跑（`node tools/probe-remote.js http://127.0.0.1:310X 3000`）。
  这样验的还是"要上线的那份探针"，而不是另写一个只在本地成立的替身。
  ★ 顺带发现的收益：一个探针同时能跑线上和本地，本身就是"它没有偷偷依赖线上特性"的证明。
- ★★ **"新版本上线了"必须验本次新增的功能，不能拿上一轮的字段充当证据**。
  `probe-remote` 原第 11 节只验道具/事件/倍率（上一轮的东西），拿它证明"技能上线"是答非所问。
  正确做法是**真的在线上把功能跑一遍**（第 12 节真的按了技能，并从快照里**反算**风向：
  拍子中心 x = `PADDLE_MARGIN + PADDLE_W/2` = 33、球场中心 (400,250)，实测 `(0.880,0.480)`
  vs 期望 `(0.876,0.482)`）—— 这才叫"上线了"。
